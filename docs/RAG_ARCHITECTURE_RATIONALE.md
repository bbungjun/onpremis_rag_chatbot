# 로컬 자가 호스팅 규정 RAG: 설계 근거와 확장 기준

> 기준: 2026-09-18 `origin/main` (`cc1df3d`). HWP/HWPX 서식 보강은 [PR #16](https://github.com/bbungjun/onpremis_rag_chatbot/pull/16)으로 병합됐다. 이 문서와 함께 추가하는 DOCX/텍스트 PDF 입력은 배포 검증과 별도로 평가한다. 로컬 작업 트리의 미커밋 시연 구성도 운영 성과로 세지 않는다.

## 1. 제품 목표와 배포 이름

직원은 연차 기한, 출장비 증빙, 개인정보 보관처럼 **회사 규정의 특정 근거가 필요한 질문**을 한다. 제품은 검색된 조문에 있는 내용만 답하고, 확인되지 않으면 그렇게 말하며, 출처를 반환한다. 답변 생성 Qwen과 임베딩 bge-m3는 호스트 Ollama에서, 규정 검색은 자체 Qdrant에서 실행하는 것이 기본 경로다.

사용자가 회사 사내망 서버를 직접 운영할 수 없으므로 현재 구현·시연 목표의 정확한 이름은 **로컬 자가 호스팅 RAG**다. 보유한 GPU PC에서 모델·애플리케이션·DB를 실행하고 접속 범위를 제한한다. 회사 사내망 서버에 동일 구성을 옮길 수 있다는 것은 설계 가능성이지 이미 달성한 온프레미스 운영 실적이 아니다. 다른 장소에서 상시 접속할 필요가 있으면 자체 관리 GPU 클라우드 VM도 후보지만 이는 클라우드 호스팅이고 GPU 임대료와 데이터 반출 정책을 따로 고려해야 한다. [EC2는 실행 시간에 따라 과금](https://aws.amazon.com/ec2/pricing/on-demand/)되고, 사설 접속 도구는 [로컬 서비스의 제한적 공유](https://tailscale.com/docs/features/tailscale-serve)를 지원한다. 어느 방식을 쓰든 실제 회사 문서는 보관·접속 승인이 확보되기 전까지 사용하지 않는다.

| 배포 대안 | 이 프로젝트에서의 역할 | 비용·보안 판단 |
| --- | --- | --- |
| 보유 GPU PC + 로컬/LAN 접속 | 지금의 개발·시연 기준 | 새 서버 구매 없이 시작할 수 있다. PC 가동 시간과 접근 경계를 직접 관리한다 |
| 자체 관리 GPU 클라우드 VM + 사설 접속 | 상시·원격 접속이 필요할 때의 후보 | [인스턴스 사용 시간](https://aws.amazon.com/ec2/pricing/on-demand/) 또는 [GPU 임대·저장량](https://www.runpod.io/pricing)에 과금된다. 회사 문서는 외부 인프라 보관 승인이 선행돼야 한다 |
| 회사 사내망 서버 | 조직이 인프라를 제공할 때의 미래 배포 | 현재 직접 운영할 수 없어 구현·검증 실적으로 적지 않는다 |

**현재 범위의 소개 문장:** 외부 생성 API의 종량 요금과 사내 규정 문맥의 외부 전송을 줄이기 위해 Qwen·bge-m3를 로컬 GPU에서 실행하고, 형식별로 추출한 규정을 항으로 검색해 조 전체를 근거와 함께 답변하는 RAG를 만든다. 현재 기본 문서의 600개 검색용 항을 검증했고, 합성 단일 HWP의 24,000개 항은 파싱까지 검증했다. 대량 Qdrant 검색·실제 OCR·운영 보안·총비용은 후속 측정 대상이다.

```text
원본 규정 Markdown / HWP 5.0 / HWPX / DOCX / 텍스트 PDF
→ 형식별 추출 및 조·항 구조 검증
→ 조(parent)·항(child) 생성
→ 항의 로컬 bge-m3 dense + 한국어 sparse 벡터
→ Qdrant에 항 벡터·조 전체 텍스트·출처 메타데이터 저장
→ 질문을 같은 방식으로 표현해 dense + sparse RRF 검색
→ 검색된 항을 조 전체로 확장하고 문맥 예산 적용
→ 호스트 Ollama의 Qwen이 근거 기반 답변 생성
→ 검색 결과에서 결정적으로 만든 출처 반환 또는 무답 fallback
```

이 데이터 흐름은 [청킹](../app/chunking.py), [수집](../scripts/ingest_md.py), [Qdrant](../app/vector_store.py), [질의](../app/rag_pipeline.py), [Qwen 클라이언트](../app/qwen_client.py)와 일치한다. 관련 결정은 [로컬 추론](adr/0001-local-inference-for-internal-policy-qa.md), [Qdrant](adr/0002-qdrant-for-local-hybrid-retrieval.md), [조/항 청킹](adr/0003-article-parent-clause-child-retrieval.md)에 남겼다.

## 2. 문서 규모: 파일 용량과 검색 규모를 분리한다

| 검증된 입력 | 원본 파일·바이트 | 내용 단위 | 구조화 결과 | 실제 DB 성능 |
| --- | --- | --- | --- | --- |
| 현재 기본 합성 Markdown | 1개, 207,536 B, 2,764줄 | 조 100개 | parent 100개, 검색용 child 600개 | 과거 소규모 평가가 있음. 현재 파일 해시에서 재측정한 검색 지표는 없음 |
| 단일 합성 HWP 규정집 | 1개, 300,544 B | 정책 1,000개, 조 8,000개 | parent 8,000개, 검색용 child 24,000개, 고유 ID 32,000개 | 실제 Qdrant 적재·검색·RAM·디스크·p95 미측정 |
| 같은 원문의 합성 DOCX | 1개, 113,090 B | 정책 1,000개, 조 8,000개 | parent 8,000개, child 24,000개·전 항 텍스트 검증 | 실제 Qdrant 적재·검색 미측정 |
| 같은 원문의 텍스트 PDF | 1개, 1,729,794 B, 890페이지 | 정책 1,000개, 조 8,000개 | parent 8,000개, child 24,000개·전 항 텍스트 검증 | 실제 Qdrant 적재·검색 미측정 |

첫 행은 현재 `datasets/docs/regulations.md`에서 직접 다시 계산했다(SHA-256 `24e5ccdfd77863dc94c6d3af20ce0c25f6d8d49e2b4da3277089fa8558e060d2`). 둘째 행은 [단일 HWP 실험](portfolio/2026-09-18-single-hwp-volume.md)의 생성·재추출 결과다(SHA-256 `c21b51d7191ca7d58df5d7141b7da50f6bfab3a1d28a80301009da732ad0de0a`). DOCX/PDF 행은 [같은 원문 두 버전 실험](portfolio/2026-09-19-docx-pdf-regulation-book.md)의 생성·재추출 결과다. 수집 코드가 child만 임베딩하므로 24,000개는 **예상 벡터 포인트 수**이고 실제 업서트 확인 수가 아니다. 합성 문구의 반복과 압축 때문에 원본 파일 바이트만으로 대규모 운영을 입증할 수 없다.

규모를 보고할 때는 파일 수·총 바이트 외에 정책/조/항 수, 실제 벡터 포인트와 저장량, 신규·개정 비율, 동시 사용자·질의율, 색인 시간·오류율, 검색 p50/p95와 근거 Recall을 함께 기록한다. 특히 현재 단일 HWP의 조항 하나가 바뀌어도 파일 전체가 변경되며, 수집기의 `--reset`은 컬렉션을 지운 뒤 재색인한다. `--reset` 없이 수정하면 사라진 조항의 기존 포인트를 삭제하는 경로가 없고, 저장소 스키마가 다르면 `ensure_collection`도 기존 컬렉션을 삭제한다. 부분 갱신·비파괴 마이그레이션·실패 후 복구는 아직 설계·검증 과제다.

## 3. 왜 Qdrant인가

현 요구는 직원 질문의 **의미 유사성**과 규정 번호·증빙 명칭 같은 **정확한 단어 일치**를 함께 찾고, 편/장/절/조 경로로 결과를 좁히는 것이다. 현재 코드는 Qdrant 한 컬렉션에 bge-m3 dense와 kiwipiepy 형태소 빈도로 만든 sparse 벡터를 넣고 RRF로 합친다. sparse의 IDF는 Qdrant 컬렉션 통계로 계산한다. 출처 경로와 조 전체 텍스트도 payload에 저장한다. [Qdrant의 dense·sparse 융합 질의](https://qdrant.tech/documentation/search/hybrid-queries/)와 [payload 필터](https://qdrant.tech/documentation/search/filtering/)가 이를 지원한다. 별도 SQL 메타데이터 DB를 운영할 필요가 없는 현재 MVP에 맞는 선택이다.

| 후보 | 이 프로젝트에서 고려한 조건 | 결정 |
| --- | --- | --- |
| Qdrant | 현재 코드의 named dense/sparse 벡터, RRF, 규정 경로 필터를 한 로컬 검색 서비스에서 처리 | 현재 채택 |
| PostgreSQL + pgvector | 기존 회사 PostgreSQL에 문서·권한·개정 이력을 통합할 때 유리할 수 있다. [pgvector는 PostgreSQL 전문 검색과 결합한 hybrid](https://github.com/pgvector/pgvector#hybrid-search)를 지원하지만, 이 저장소에는 현재 운영 PostgreSQL이 없다 | 관계 데이터 요구가 확인되면 재평가 |
| Milvus | [dense·sparse 검색](https://milvus.io/docs/milvus_hybrid_search_retriever.md)과 분산 확장 후보. 공식 standalone Compose도 별도 구성요소를 운영한다 | 이 프로젝트의 실제 24,000포인트 미측정 상태에서 도입 이유가 없음 |

이 표는 **요구사항 적합성 판단**이다. 같은 코퍼스·하드웨어에서 DB별 색인 시간, Recall, 지연, RAM/디스크, 운영 비용을 비교하지 않았으므로 “Qdrant가 가장 빠르다”는 주장은 하지 않는다. 현재 구현도 필터 조건은 만들지만 payload 인덱스는 생성하지 않는다. 필터가 빈번해지면 [실제 사용 필드의 인덱스](https://qdrant.tech/documentation/manage-data/indexing/)를 측정 후 추가해야 한다.

과거 50개 held-out 질문에서 dense-only의 정답 조 Recall@5는 0.96, RRF는 1.00(+4%p)였다. 이는 **검색 전략 비교**이지 DB 제품 비교가 아니다. 50문항 paired bootstrap 95% CI가 `[0.00, 0.10]`이며, 당시 문서 해시는 `4ecef7ee…`로 위 현재 기본 문서와 다르다. [원 평가](portfolio/2026-08-31-rrf-ablation-reranker-evaluation.md)를 현재 대형 HWP의 품질 지표로 옮겨 쓰지 않는다.

## 4. 왜 형식별 추출과 조/항 청킹인가

실제 규정은 문단 경계보다 제N편·장·절·조·항의 의미 경계가 중요하다. HWP/HWPX는 고정된 HWP CLI v0.17.0으로 Markdown을 추출한 뒤 자동 제목 번호와 합쳐진 조·항을 정규화한다. 조 제목 후보 수와 생성된 parent 수가 다르면 실패한다. [HWP 조항 파싱 기록](portfolio/2026-09-18-hwp-article-parsing.md)은 가지 조항과 합쳐진 문단의 재현 범위를 보여준다. [PR #16](https://github.com/bbungjun/onpremis_rag_chatbot/pull/16)은 표·각주·이미지 글자/캡션 보강을 추가했다. 이 브랜치의 DOCX/텍스트 PDF 입력은 같은 조·항 검사에 연결하지만, 탐지 가능한 DOCX 자동 번호·병합 표·인라인 이미지는 실패시키며 PDF 표의 셀 관계는 보존하지 않는다. 실제 사내 문서의 형식별 정확도는 미검증이다.

청킹에서는 항을 검색 단위로, 조 전체를 Qwen에 주는 설명·인용 단위로 사용한다. 고정 문자 수로 자르면 항의 조건과 조 번호가 서로 다른 조각으로 갈라질 수 있고, 조 전체만 벡터화하면 긴 조의 세부 항이 검색에서 약해질 수 있다는 설계 판단이다. 현재 수집은 child만 임베딩하고 각 child payload에 `parent_text`를 복제한다. 검색 후 `(document_id, parent_id)`로 조를 묶고 기본 설정에서는 상위 5개 조를 사용한다. 이 청킹 자체의 우위를 고정 길이·조 전체 색인과 같은 조건에서 비교한 실험은 없다. 긴 조와 반복된 `parent_text`는 문맥 예산과 저장량을 늘린다. 현재 문맥 제한은 글자 수 휴리스틱이므로 토큰 단위 검증도 필요하다.

실제 문서를 받을 때는 서식별 표본을 고정하고 조·항 누락, 표의 열/값, 각주 귀속, OCR 글자·캡션, 출처 경로를 사람이 만든 정답과 비교한다. 검증되지 않은 문서를 조용히 색인 성공으로 처리하지 않는 것이 우선이다.

## 5. 보안과 비용 경계

**로컬 추론이 해결하는 것:** 기본 Qwen/bge-m3 호출은 자체 Ollama로 향하므로 외부 LLM API의 질문별 토큰 요금이 발생하지 않고, 기본 생성 경로의 문맥을 외부 모델 API로 보내지 않도록 설계할 수 있다. **별도로 확보해야 하는 것:** 서버·GPU 구입 또는 임대, 전력, 백업, 모니터링, 접근 제어, 네트워크 격리, 모델·이미지 공급망 관리, 운영 인력 비용이다. 원본과 질의가 “절대 외부로 나가지 않는다”는 주장은 실제 배포의 egress·로그·비교 기능을 확인해야 가능하다.

현재 main의 개발용 `docker-compose.yml`은 6333·8000·8501 포트를 호스트에 publish하고 Qdrant 이미지에 `latest` 태그를 사용한다. `.env.example`은 Gemini 비교 엔드포인트·패널을 켠다. README의 `shared-ec2` 팀 설정은 원격 Ollama 개발 경로이므로 로컬 데이터 경계로 간주하지 않는다. [Qdrant 공식 보안 안내](https://qdrant.tech/documentation/security/)도 자체 호스팅 인스턴스는 인증·TLS·바인딩을 직접 구성해야 한다고 명시한다. 또한 과거 instruct 모델의 무답·주입 평가에서 canary 유출 9/15가 관찰됐다([평가 기록](portfolio/2026-09-06-think-mode-and-instruct-model.md)). 따라서 현재 기본 구성을 “보안이 검증된 사내 서비스”라고 표현하지 않는다. 별도의 로컬 시연 작업은 LAN HTTPS와 내부 포트 분리를 시험했지만 main에 병합되지 않았고, 무로그인·문서별 권한 부재 등 운영 한계가 남아 있다.

비용 비교는 같은 질문량·품질·운영 시간에서 해야 한다.

```text
외부 API 월 비용 = 질문 수 × (평균 입력 토큰 × 입력 단가 + 평균 출력 토큰 × 출력 단가)
                 + 임베딩·저장·네트워크 비용
로컬 PC 월 비용 = 장비 감가 + 전력 + 저장·백업 + 운영·장애 대응
GPU VM 월 비용 = 사용 시간 × GPU 인스턴스 단가 + 저장·네트워크·백업 + 운영·장애 대응
```

질문량·토큰·가동 시간·전력·운영 시간의 동일 조건 측정값이 없어 손익분기점이나 절감액은 **측정하지 않음**. 보유한 GPU PC를 쓰면 새 장비 구매의 즉시 지출을 피할 수 있다는 판단은 가능하지만 가용성·전력 비용을 없애지는 않는다. 클라우드 VM은 외부 LLM API가 없어도 [GPU 사용 시간과 저장량에 따라 과금](https://www.runpod.io/pricing)된다. 회사 문서를 개인 PC나 외부 VM에 보관하는 것은 조직의 데이터 취급 승인이 필요하다.

## 6. 다음 구현 순서와 완료 기준

1. **배포 경계 확정:** 로컬 PC 시연과 외부 접속 운영을 분리한다. 기본 제품 경로에서 Gemini 비교·클라우드 자격증명을 제거하거나 명시적으로 차단하고, Qdrant/API의 외부 공개를 막는다. 이미지 버전을 고정한다. 실제 직원 사용 전 인증·문서별 권한, TLS, 백업 복구, egress 검증과 주입 공격 재평가가 필요하다.
2. **실제 문서 충실도:** DOCX·텍스트 PDF·HWP/HWPX의 대표 문서에서 조·항·표·각주·이미지 정답 세트를 만든다. 실패와 누락을 포함한 추출 결과를 보존한다.
3. **규모 실험:** 합성 HWP의 24,000 child부터 실제 Qdrant 적재 수·색인 시간·RAM/디스크·질의 p50/p95를 측정한다. 이후 같은 분포의 10배 청크를 별도 단계로 시험한다. 고정된 사람 작성 질문으로 Recall, 출처, 무답, 생성 지연도 확인한다. 기준을 통과하지 못하면 payload 인덱스, 배치, 문맥 길이 또는 DB 선택을 다시 검토한다.
4. **갱신·복구:** 문서 해시와 조항 버전을 기록하고, 단일 HWP 변경 때 전체 컬렉션 삭제를 피한다. [Qdrant alias의 원자적 전환](https://qdrant.tech/documentation/manage-data/collections/#collection-aliases)을 후보로 두되 실제 장애 복구 시험 후 채택한다.
5. **비용 검증:** 예상 사용자 수·질문량과 운영 시간을 확정하고 로컬 PC, 전용 GPU VM, 외부 API의 동일 질문·품질 조건 총비용을 비교한다. 측정 전에는 “API 종량 요금을 피하는 구조”로만 설명한다.

성공 기준의 p95, 동시 사용자 수, 허용 OCR 오류율과 월 예산은 아직 합의되지 않았다. 이 값을 정한 뒤 규모 및 운영 판단을 숫자로 내릴 수 있다.
