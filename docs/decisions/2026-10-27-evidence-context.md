# 연결 근거 선택과 문맥 보존 — 의사결정 기록

## D01 — 작업 범위와 기록 방식

- 관찰: 10월 26일 합성 복합 질문 12개 중 후보 근거 충족 12/12,
  최종 문맥 근거 충족 9/12. 후보 선택 1건, 문맥 잘림 2건을 재현했다.
- 대안: GraphRAG 전환, 검색 후보 수 확대, 기존 후보 내 선택과 문맥 구성 개선.
- 선택: 기존 후보 안에서 개선한다. 관계를 찾기 위한 새 모델·DB는 추가하지 않는다.
- 이유: 누락된 세 조문 모두 기존 후보에 있었다. 추가 검색만으로 문맥 손실은 해결되지 않는다.
- 범위: RAG 질의와 새 문맥 정책 모듈, 진단 평가·회귀 테스트·문서. 수집·벡터 저장소·Ollama
  클라이언트 파일은 수정하지 않는다. 기존 PR #21을 구현 및 검증 결과로 갱신한다.
- 기록: 사용자 요청을 AGENTS.md와 이 디렉터리에 명시하여 이후 작업에도 지속한다.

## D02 — 선택 정책과 안전한 축약

- 대안: 전체 조문 뒤에서 제거, 문자 단위 절단, LLM 요약, 항 단위 발췌.
- 선택: 검색의 최상위 조문을 앵커로 유지하고, 질문 어휘와 제목 관련성 및
  같은 문서의 명시적 참조를 사용해 후보를 정렬한다. 조문 번호만 같은 외부 법률과
  다른 문서를 연결하지 않는다. 검색 후보 밖의 원문은 가져오지 않는다.
- 문맥 예산이 부족한 경우 정의·서식·일반 제재 대신 적용 대상·절차·예외를
  원문 항 단위로 보존한다. 질문이 제재·서식·정의를 요구하면 해당 항도 보존한다.
- 단어·문장 중간 절단과 생성 요약은 하지 않는다. 예외나 부정 조건을 잃은
  불완전한 항으로 답변하지 않으며, 하나의 근거도 예산에 들어가지 않으면 fallback한다.
- 한계: 어휘와 명시적 참조만으로 의미 관계 전체 또는 질문의 모든 요구를 보장하지 않는다.
  문자 예산은 기존 휴리스틱이며 토큰 수 검증을 대신하지 않는다.
- 상태: 구현 전 선택. 개발 진단과 별도 고정 평가 결과를 확인해 채택 여부를 갱신한다.

## D03 — 평가 분리와 채택 기준

- 기존 16문항과 실패 사례는 개발·회귀 진단으로만 사용한다.
- 별도의 복합·단일·문서 부재 질문을 구현 검증 전 고정하고 SHA-256을 기록한다.
  동일 에이전트가 문서를 보고 만든 합성 질문이며 사람 검수 또는 독립 사용자 평가가 아니다.
- 같은 검색 결과에 baseline/선택만/축약만/통합을 적용해 단계를 분리한다.
- 필요한 조문의 전체 포함뿐 아니라 원문 요구 사실의 문맥 포함, 문자 예산,
  문서 경계, 조건·예외 보존과 빈 문맥 fallback을 검증한다.
- 채택 기준: 기존 재현 세 건 해결, 단일 질문의 정답 근거 회귀 없음,
  고정 평가의 전체 근거·요구 사실 보존이 baseline보다 나쁘지 않음,
  예산 초과 0건, 출처 없는 생성 호출 0건. 실패도 모두 남긴다.
- Qwen은 답변 생성에만 사용한다. 답변 비교를 수행하면 동일 로컬 모델·프롬프트·설정으로
  실행하고 에이전트 검토와 자동 문자열 점검을 사람 평가나 운영 정확도로 표현하지 않는다.
- Docker 없는 Qdrant Local 진단과 실제 Compose 서버 검증을 구분한다.

## D04 — 첫 개발 재생에서 발견한 회귀와 수정

- 구현 전 기존 세 누락 재현은 3 failed였고, 첫 구현 후 세 재현 및 관련 테스트 41개가 통과했다.
- 개발 16문항 전체 재생에서는 복합 11/12, 대조 4/4였다. 기존 m05 위탁 계약 질문에서
  계약 전결 조문을 밀어내는 새 회귀를 발견했다. 첫 실패 결과를 숨기지 않는다.
- 원인: 어휘 겹침만의 재정렬은 원래 높은 검색 순위의 근거를 과도하게 낮출 수 있다.
  또한 참조 지지도 계산에 제목의 자기 조문 번호가 포함되는 것을 발견했다.
- 선택: 기존 검색 순위에 감소하는 사전 가중치 `6 / (rank + 1)`를 두어 재정렬을
  완화하고, 자기 참조는 참조 지지도에서 제외한다. 문서별 참조와 어휘는 그대로 사용한다.
- 회귀 고정: m05도 고정 검색 입력에 추가한다. 수치는 개발 세트 기반 휴리스틱으로 표시한다.
- 별도 검증 세트: 복합 12·단일 4·문서 부재 4, 총 20문항을 결과 확인 전 고정했다.
  SHA-256 `725b3c0e733b0fda18d97d57f4ac14b47f9e1aded76b1a50d74d8c8085ff0d40`.
  현재까지 검증 세트에서는 정답 사실이 지정한 원문 조문에 존재하는지만 검사했고,
  검색·생성 결과는 아직 열지 않았다. 이후 최종 결과를 보고 이 세트로 튜닝하지 않는다.

## D05 — 보수적인 항 구조 인식과 비교 실행 고정

- 검토 중 번호가 같아도 항의 의미가 다른 문서를 축약할 위험을 발견해 실패 테스트로 재현했다.
- 선택: 번호와 알려진 라벨을 함께 확인한 항만 생략 후보로 삼는다. 알 수 없는 라벨,
  비구조 문서, 모든 적용 대상·절차·예외는 그대로 유지한다.
- 개발 재생 최종 결과: 복합 12/12, 대조 4/4의 정답 조문이 문맥에 포함됨.
  이는 정답 사실이나 실제 답변의 정확도와 별개다.
- 4개 구성 정책을 같은 검색 결과에서 비교한다. baseline은 변경 전 `1359a0a`의
  실제 RAG 문맥 코드로 고정한다. 결과와 전체 프롬프트는 로컬 reports에 저장한다.
- 별도 검증 20문항 외에 기존 단일 조문 50문항을 회귀 세트로 함께 실행한다.
  기존 50문항을 새 독립 holdout 성과로 부르지 않는다.
- 생성 비교는 설치된 `qwen3:4b-instruct`, temperature=0, seed=42, num_ctx=4096,
  num_predict=512로 고정하고 A/B 순서를 문항마다 교대한다. 제품 기본 모델은 바꾸지 않는다.

## D06 — 로컬 실행 차단과 재시도

- 첫 비교 실행 r1은 Ollama 모델 목록 요청에서 연결 거부로 종료됐다.
  검색·생성 결과를 보지 않은 실패이며 `context-preservation-20261027-r1/failure.json`에 보존했다.
- 호스트 Ollama만 숨김 프로세스로 시작한 뒤 같은 데이터·코드로 새 r2를 실행했다.
  컨테이너에 Ollama를 넣거나 외부 모델 API로 전환하지 않았다.
- 필수 Compose 명령은 이 격리 worktree에 `.env`가 없어 exit 1,
  localhost:6333 연결은 exit 7이었다. 사용자의 원래 `.env`를 복사하거나 수정하지 않았다.
- 관련 자동화 검증은 45 passed, 전체 로컬 테스트는 353 passed / 9 skipped,
  Ruff check 및 format check 통과. 이 수치는 답변 품질 지표가 아니다.
- r2는 baseline/선택만/축약만/통합의 프롬프트와 결과를 보존한 뒤
  고정 20문항의 baseline/통합 답변을 생성한다. 실행 완료 후 채택 기준을 판정한다.

## D07 — 평가 도구의 단계 정의와 답변 검토 기준

- 기존 진단 스크립트의 parent 단계도 새 정렬 정책을 사용하도록 갱신한다.
  기존 상위 5개와 새 문맥을 비교하면, 새 정책이 복구한 근거를 계속 누락으로
  분류할 수 있기 때문이다. 과거 산출물은 덮어쓰지 않는다.
- 새 고정 세트의 조문 전체 포함은 복합 8/12 → 12/12, 단일 4/4 → 4/4였다.
  실제 답변 생성 결과를 읽기 전까지 이 수치는 근거 전달 성과로만 해석한다.
- 답변 검토 기준: 질문이 요구한 사실·조건의 완전성, 원문과의 모순/추측 부재,
  실제 전달한 조문과 맞는 출처 표기를 각각 확인한다. 하나라도 실패하면 전체 성공으로 세지 않는다.
- 문서 부재 질문은 문서에서 확인 불가를 명시하고 미지원 금액·요일·비율을 만들지 않아야 통과다.
- 에이전트 단독 검토이며 블라인드 사람 평가 또는 독립 Judge 평가가 아니다.
  생성 길이 종료와 부분 답변도 실패 기록에 남긴다. 검토를 보고 정책을 다시 튜닝하지 않는다.

## D08 — 최종 결과와 채택 범위

- 개발 복합 근거 포함은 9/12 → 12/12, 별도 고정 복합은 8/12 → 12/12,
  단일 회귀 50문항은 49/50 → 50/50. 기존에 포함하던 정답 근거의 회귀는 없었다.
- 고정 복합에서 선택만/축약만은 각각 11/12, 통합은 12/12였다.
  사전 지정 요구 사실의 문자열 포함은 9/12 → 12/12. 이는 의미적 답변 정확도가 아니다.
- 총 86문항 × 4정책의 344개 문맥 구성에서 문자 예산 초과는 0건이었다.
- Qwen 답변 40건을 모두 수집했다. baseline v08과 통합 v09가 길이 한도에서 종료됐다.
  문서 부재 질문 네 개는 두 정책 모두 미지원 금액·요일·비율을 만들지 않고 확인 불가를 답했다.
- 답변의 잔여 오류를 별도 보존했다. 통합 v01/v06의 출처 세부 위치 오류,
  v09의 근거가 있어도 잘못된 확인 불가, v10의 요구 항목 누락,
  v12의 예외 해석 손실, v16의 불필요한 확인 불가 등이 있었다.
  특히 v10/v16은 baseline보다 나쁜 답변이 관측된 사례다.
- 선택: **근거 누락 세 건의 코드 수정과 평가 공백 보완은 완료**, 근거 정책의
  오프라인 실험 기준은 충족했다. 그러나 **전체 답변 품질의 운영 채택은 보류**한다.
  PR은 Draft로 유지하고, 이번 변경을 답변 정확도 개선이나 운영 성과로 표현하지 않는다.
- 검토 후 검증 세트로 프롬프트나 선택 정책을 추가 튜닝하지 않았다.
  다음 과제는 별도 개발 질문에서 복합 질문의 요구 항목·판정 지시·인용 검증을 분리하고,
  새로운 고정 세트로 생성 품질의 회귀를 확인하는 것이다.
- 실제 `answer_question` → 호스트 임베딩 → 고정 검색 callback → 실제 Qwen 경로도 1건
  확인했다. 평가 프롬프트와 출처 ID가 일치했으며, 이 검사는 서버 검색 또는 답변 정답률 검증이 아니다.
