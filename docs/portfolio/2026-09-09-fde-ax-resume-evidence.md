# FDE·AX 지원용: 사용자 관점의 RAG 평가 재설계

## 현재 이력서에 사용할 핵심 bullet

> 팀 리더로서 조항 번호·문서 용어에 의존한 RAG 평가의 사용자 대표성 문제를 발견하고,
> 직원 관점의 일상어 50문항과 정답 근거 조항을 연결한 평가셋 재설계를 주도.

분량이 더 짧아야 하는 경우:

> 사내 규정 RAG의 평가 질문을 직원 일상어 50문항으로 재구성하는 평가 재설계를 주도하고,
> 정답 조항 기반 검증 기준 마련.

50은 평가 문항 수이며 정확도나 개선율이 아니다. 위 문구의 개인 기여는 사용자가 밝힌
문제 제기와 팀 의사결정 주도에 한정한다. 임베딩·모델 구현 전부를 단독 수행했다고 쓰지 않는다.

## 프로젝트 설명 한 줄

> 외부 LLM API 비용과 사내 정보 반출 제약이 있는 기업 환경을 가정해, 로컬 모델 기반
> 사내 규정 RAG 챗봇 PoC를 기획하고 팀 개발 방향을 수립.

이 요구사항은 사용자의 설명상 기사에서 착안한 가정이다. 실제 고객사 요구 수집, 폐쇄망 운영
인증, 현업 배포, API 비용 절감 실적으로 확대하지 않는다. 평가 문서는 합성 사규이며 실제
직원 질문 로그로 대표성을 검증한 프로젝트가 아니다.

## Before / 문제

팀은 Gemini와 Qwen의 답변을 보고 주관적으로 만족했지만, 다른 사람에게 품질을 설명할
평가 근거가 부족했다. 사용자는 팀장으로서 LLM-as-Judge 방법의 검토를 제안했다.

이후 조항 번호나 규정집 용어를 질문에 넣은 평가를 보고, 일반 직원은 정답이 들어 있는
조항을 미리 알고 질문하지 않는다는 점을 지적했다. 문제는 조항 조회 자체가 잘못됐다는 것이
아니라, 이런 질문을 일반 직원 대상 챗봇의 주 평가로 사용하는 데 있었다.

## Why / 판단과 선택

조항 번호는 검색 대상에 대한 강한 단서가 될 수 있다. 직원 질문을 평가하려면 직원이
표현할 만한 질문으로 검증해야 한다는 방향으로 평가 대상을 다시 정의했다.

이 변경은 학습 데이터 누수를 입증·제거한 작업으로 표현하지 않는다. 번호 제공이 점수를
얼마나 부풀렸는지 통제 실험하지 않았으므로, 편향 제거 효과나 정확도 향상도 주장하지 않는다.

LLM-as-Judge는 반복 실행할 수 있는 평가 방법이다. 모델이 평가한다는 이유만으로 객관적이거나
정확한 것은 아니다. 이후 EXAONE 오독이 발견됐으므로 Judge 점수를 성과의 주된 근거로 쓰지 않는다.

## Solution / 확인된 변경

커밋 `03e84df`에서 평가 데이터와 설계/계획 문서가 변경됐다.

| 항목 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 총 질문 | 76 | 50 |
| 일상어 질문 | 41 | 50 |
| 조항용어 질문 | 35 | 0 |
| 명시적 제N조 포함 질문 | 27 | 0 |
| 고유 정답 조항 | 66 | 45 |

기존 일상어 41개를 의미 기준으로 유지하고 신규 질문 9개를 추가했다. 기존 질문 40개는
문자열도 같고 1개는 표현이 바뀌었다. 유지된 41문항의 gold_jo는 보존됐다. 일부 기준 답변도
바뀌었으므로 모든 정답을 고정한 순수 질문 표현 실험은 아니다.

이어서 `e757a2b`에서 별도 Judge, 실행기와 관련 테스트가 추가됐다. 검색된 정답 조항의
반환 여부와 생성 답변 채점을 구분할 수 있는 구조가 마련됐다. 초기 Judge에는 전체 검색
문맥을 주지 않았으므로 그 groundedness 점수를 조문 전체에 대한 근거성 검증으로 설명하지 않는다.

## Verification / 근거 확인

2026-09-09 저장소 기록을 읽어 확인했다. 이번 작업은 이력서 근거 정리이며 모델을 새로 호출하거나
새로운 품질·지연 벤치마크를 실행하지 않았다.

- `git show 03e84df^:datasets/eval/qa_set.jsonl`와 변경 후 파일 비교: 문항 유형, 조항 번호,
  질문 보존, gold 조항 범위를 확인.
- `tests/test_evaluate_local_judge.py`: 문항 수, 연속 ID, 조항 번호 없는 질문, 존재하는 gold 조항
  참조에 관한 검사 확인. 이는 구조 검사이며 문장 의미나 사용자 대표성을 보증하지 않는다.
- `scripts/evaluate_local_judge.py`: 정답 조항 반환 지표와 Judge 채점 분리 확인.
- 사용자의 설명: 팀장으로서 문제 정의, 세 작업 분야 분담, 평가 도입 제안, 질문 유형 철회 제안.
  개인 의사결정의 근거는 사용자 진술이며 Git 작성자만으로 그 기여를 추정하지 않았다.

## After / 주장할 수 있는 성과

현재 성과는 **일반 직원 관점으로 평가 대상을 재정의하고 재사용할 평가셋을 마련한 것**이다.
정확도·응답 시간·현업 업무시간이 개선됐다는 실험은 이 변경에서 수행하지 않았다.

평가 질문 내 조항 번호 노출은 27건에서 0건이 됐지만, 고유 정답 조항 범위는 66개에서
45개로 줄었다. 따라서 전체 커버리지를 넓혔다고 쓰지 않는다. 실제 직원 로그를 수집한 것은
아니므로 현업 대표성 향상을 측정했다고도 쓰지 않는다.

## 면접 설명 초안

“외부 API 비용과 정보 반출 제약이 있는 환경을 가정해 로컬 사내 규정 RAG를 제안했습니다.
팀 답변은 보기에는 괜찮았지만 품질을 설명할 기준이 없어서 자동 평가를 검토하자고 했습니다.
평가 질문에 조항 번호가 들어 있는 것을 보고, 일반 직원의 사용 방식과 맞지 않는다고 판단해
일상어 질문 중심으로 바꾸자고 제안했습니다. 결과물은 일상어 50문항과 정답 조항을 연결한
평가셋입니다. 다만 이것을 정확도 개선이라고 주장하지 않고, 이후에는 Judge의 오독까지
발견해 채점기 자체도 검증해야 한다는 점을 확인했습니다.”
