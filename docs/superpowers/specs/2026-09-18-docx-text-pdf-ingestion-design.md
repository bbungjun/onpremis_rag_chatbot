# DOCX와 텍스트 PDF 규정 수집 첫 단계 (2026-09-18)

## Before / 문제

현재 수집은 Markdown·HWP·HWPX만 발견한다. 사내 규정이 DOCX 원본이나 텍스트 PDF 배포본으로 제공되면 색인할 수 없다. 같은 규정의 DOCX와 PDF를 한 폴더에 넣으면 현재 경로는 각각 다른 `source_path`로 다루므로 중복 색인이 된다.

## Why / 선택

사용자가 우선 선택한 PDF 범위는 글자를 선택할 수 있는 텍스트 PDF다. DOCX는 문단·표 순서를 얻을 수 있지만, [PDF에는 제목·표·문단의 의미 계층이 보장되지 않는다](https://pypdf.readthedocs.io/en/latest/user/extract-text.html). 따라서 두 형식을 같은 원본처럼 평탄화하되 성공 기준은 기존 규정의 조·항 구조 검증으로 둔다. 스캔 PDF는 이번 단계에서 OCR 결과를 추측하지 않고 실패한다.

`read_document(path) -> str`을 입력 모듈의 interface로 유지한다. DOCX에는 `python-docx`의 문단·표 순서 이터레이터를, PDF에는 `pypdf`의 페이지 텍스트 추출을 쓴다. 생성한 텍스트를 기존 규정 정규화·청커에 연결한다. DOCX의 단순 표는 헤더·값 관계를 보존하고, 자동 번호·이미지·복잡한 병합 표 같은 미지원 구조가 손실될 때는 조용히 성공하지 않도록 범위를 명시한다.

같은 상대 경로·파일명 줄기의 DOCX/PDF 쌍은 한 논리 문서의 서로 다른 표현일 가능성이 있으므로 수집 전에 명시적으로 거부한다. 게시된 PDF와 편집용 DOCX 중 권위 있는 원본을 운영자가 선택한다. 문서 해시만으로 중복을 추측하지 않는다.

## Solution / 변경 범위

- DOCX와 텍스트 PDF를 기존 문서 리더와 수집 파일 탐색에 추가한다.
- DOCX 문단·표를 순서대로 구조화 Markdown으로 만들고, PDF 페이지 텍스트에서 조·항 경계를 복원한다.
- 텍스트가 없는 PDF, 조·항이 없는 추출 결과, 같은 이름의 DOCX/PDF 쌍을 색인 전에 거부한다.
- 작은 합성 규정 DOCX/PDF fixture를 고정하고 원본 조항의 추출·청킹·출처 경로를 회귀 검사한다.
- HWP/HWPX 동작, Qdrant 스키마와 답변 모델 경로는 유지한다.

## 검증과 한계

테스트를 먼저 실패시키고 구현 후 같은 시나리오를 통과시킨다. 전체 pytest/Ruff, 문서 시각 검증, Docker 필수 명령과 Git diff를 확인한다. PDF 표의 셀 관계·페이지 좌표 인용, 스캔 OCR, DOCX 자동 번호·각주·이미지, 실제 사내 문서 다양성은 이번 첫 단계에서 측정하거나 지원한다고 주장하지 않는다.
