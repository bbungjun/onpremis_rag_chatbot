# 로컬 자가 호스팅 규정 RAG 설계 근거 문서화 (2026-09-18)

## Before / 문제

README는 구성요소와 과거 평가를 보여주지만, 문서 규모·Qdrant 선정·HWP 파싱·조/항 청킹이 사용자 목표인 내부 문서 보호와 외부 LLM API 비용 회피에 어떻게 연결되는지 한곳에서 설명하지 않는다. 사용자는 회사 사내망 서버를 운영할 수 없으므로 실제 현재 목표를 로컬 자가 호스팅으로 정확히 불러야 한다. 기존 600개 항 코퍼스의 검색 평가와 24,000개 항 합성 HWP의 파싱 검증을 같은 규모의 성과로 오해하기 쉽다. 기본 Compose의 포트 공개와 Gemini 비교 설정은 보안 목표와 현재 구현 사이의 차이도 만든다.

## Why / 정리 원칙

- 재현 가능한 코드·데이터·평가 기록을 사실의 기준으로 삼는다. 메인 브랜치, 열려 있는 HWP 서식 PR, 추적되지 않은 시연 작업을 구분한다.
- 파일 수, 원본 바이트, 정책/조/항 수, 실제 벡터 수, 갱신 범위, 질의 부하를 별도 규모 축으로 쓴다.
- Qdrant 선택은 요구사항 적합성으로 설명하고, 다른 벡터 저장소보다 빠르거나 저렴하다는 미실험 주장은 하지 않는다.
- 로컬 추론은 외부 API의 토큰별 요금을 피하는 설계다. 하드웨어·전력·운영 비용과 네트워크 보안은 따로 측정·구성해야 한다.
- 제품 용어를 `CONTEXT.md`에, 변경 비용이 큰 결정 세 개를 ADR에, 전체 근거와 다음 검증을 독립 문서에 둔다.

## 산출물과 범위

`docs/RAG_ARCHITECTURE_RATIONALE.md`는 현재 데이터 흐름, 선택 이유, 대안, 측정 증거, 한계, 확장 게이트를 설명한다. `docs/adr/`에는 로컬 추론 경계, Qdrant, 조/항 parent-child 결정을 기록한다. `docs/portfolio/2026-09-18-onprem-rag-architecture-rationale.md`는 Before/Why/Solution/Verification/After 증거를 남긴다. README에는 이 설명의 입구만 추가한다. 런타임 코드와 기존 평가 수치는 바꾸지 않는다.

## 검증 방법

문서 수치와 구현 설명을 실제 파일·청킹 결과·평가 기록에 대조한다. Markdown 링크, Git diff, Ruff 및 기존 pytest를 확인한다. AGENTS.md의 Docker 런타임 명령을 시도하고 불가하면 차단 원인을 기록한다. 문서 작업은 성능·정확도 향상으로 보고하지 않는다.
