# 단일 HWP 규정집 설계 (2026-09-18)

## Before / 문제

이전 실험은 합성 정책 1,000개를 HWP 파일 1,000개로 생성했다. 실제로 한 권의 규정집을 입력하는 시나리오와 다르다. 현재 청커는 `제N조` 번호를 청크 ID로 사용하므로 여러 규정을 한 파일에 합칠 때 조 번호가 다시 `제1조`부터 시작하면 parent/child ID가 충돌한다. Qdrant는 파일 단위가 아니라 검색용 child 포인트를 저장하므로 원본 파일 수만으로 검색 규모가 결정되지는 않는다.

## 선택

기본 생성물을 **단일 HWP 5.0 규정집**으로 바꾼다. 10개 주제를 편, 20개 조직을 장, 5개 고용 형태를 절로 배치하고, 조 번호는 규정집 전체에서 1~8,000으로 이어지게 한다. 이 구조는 현 청커의 조 ID 계약을 유지하며 같은 파일 안에서 ID 충돌을 피한다. 기존 1,000개 파일 생성은 비교 실험용 `split` 모드로 남긴다.

두 형식은 같은 1,000개 합성 정책과 24,000개 검색용 항을 담는다. 단일 HWP는 배포·보관 단위가 한 권이지만, 한 조만 바뀌어도 전체 파일의 해시가 바뀐다. 기존 파이프라인은 파일별 변경 감지를 구현하지 않았으므로 단일 파일 변경 시 전체 재색인이 필요하다. 이는 성능 개선 주장이 아니라 문서 구성 선택이다.

## 인터페이스와 검증

- 생성 CLI 기본값은 `book`; `--layout split`로 이전 다중 파일 생성물을 재현한다.
- 단일 HWP와 원본 Markdown을 생성하고, HWP CLI 유효성·재추출·8,000 parent/24,000 child·전역 청크 ID 고유성을 검사한다.
- 개발 질문에는 단일 파일 경로와 전역 조 번호를 기록한다. 생성 질문은 독립 홀드아웃으로 취급하지 않는다.
- 실제 Qdrant 적재, 검색 지표, Qwen 답변 품질은 Docker/Ollama 런타임이 가용해진 뒤 별도 측정한다.
